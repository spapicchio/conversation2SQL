# deep_agent

A BIRD-Interact evaluation baseline.

## What it does

`deep_agent` resolves an **ambiguous** user query against a Postgres database under
the bird-coin patience budget — same task as the `bird_full` baseline. The difference:
instead of dedicated schema tools (`get_schema`, `get_table_names`, …), the agent
explores the database through a **single read-only `bash` tool** over an on-disk
per-task catalog directory (with `cat`, `ls`, `find`, `grep`, `head`, `tail`, `wc`),
and runs read-only SQL with `psql` through the same tool. Everything else — the
patience budget, `ask_user`, `submit_sql` — is reused unchanged from `bird_baseline`.

Selected via `ConfigPipeline.baseline = deep_agent`; entry point
`run_agent_deep_agent` in `agent_code.py`.

## How it works

**Catalog materialization** (`catalog_seed.py`, `materialize_catalog_dir(task)`) —
creates a fresh temp dir per task run, populated from
`<TaskData.deep_catalog_root>/<selected_database>/` (generated by
`scripts/generate_catalog.py`) and from `masked_agent_kb`:

| Path | Source | Rendering |
|------|--------|-----------|
| `<tmp>/database_overview.md` | `<catalog>/<db>/database_overview.md` on disk | copied if present (silently skipped if absent); any `## Knowledge Base` section already on disk (rendered by `generate_catalog.py` from the full, unmasked KB) is stripped and replaced with one rendered fresh per task from `masked_agent_kb` — name → exact `knowledge_base/<file>.md` → description |
| `<tmp>/tables/<table>.md` | `<catalog>/<db>/tables/*.md` on disk | read verbatim (DDL + columns w/ descriptions + FKs) |
| `<tmp>/tables/_foreign_key_constraints.md` | disk | all PK/FK constraints in the db |
| `<tmp>/knowledge_base/<node>.md` | `masked_agent_kb` | one file per surviving node, re-rendered via `linearize_prerequisites` (node name used as-is, unsanitized); masked prerequisites never appear |

The KB (both the individual files and the index in `database_overview.md`) is
re-rendered per task from `masked_agent_kb` (never trusted from the on-disk file), so
per-sample masking is faithful: a masked entry is never collected and its dangling
edge/index line never renders. `deep_catalog_root` is set per run (e.g.
`data/bird_interact/catalog_bird_interact_lite`); a missing `<db>/tables/` directory
raises `FileNotFoundError`. The temp dir is cleaned up in a `finally` block after each
task run.

**Tools (3)** — `bash` (read-only shell + psql), `ask_user`, and `submit_sql`. The
`bash` tool validates commands against a whitelist (`cat`, `ls`, `find`, `grep`, `head`,
`tail`, `wc`, `psql`) and a shell-metachar denylist (`; & > < \` $( ${ \n`); `psql`
commands are additionally screened by the reused `_violates_psql_guardrail`. Writes are
rejected server-side via `PGOPTIONS="-c default_transaction_read_only=on"`.

**Build** — `create_agent` (not `create_deep_agent`) with explicit middleware
composition. This keeps every toggle local to one agent build (no globally-registered
state that concurrent runs with different flags could clobber). The system + user turns
travel together in the initial state (like `bird_baseline`); there is no longer a
second middleware-injected system message to dodge, so the system prompt rides the
message history directly instead of going through `create_agent`'s `system_prompt=`.

**Patience budget** — the same middleware appended last in the same relative order as
`bird_baseline` (`check_budget_limit` → `sanitize_thinking_history` →
`wrap_model_append_tool_message` →
`tool_wrapper_patience_and_submit`), imported from `bird_baseline/agent_callback.py`.
`bash` costs 1.0 coin (flat, tunable); `submit_sql`/`ask_user` reuse the shared
`TOOL_COSTS` table.

## Ablations

All default to `False` → minimal agent. The flag is threaded `ConfigReader` → `TaskData`
(like `enable_psql_console`), gated in `_build_deep_middleware`, paired with a prompt
block and a run-dir slug suffix.

| Flag | Adds | Tools | Slug |
|------|------|-------|------|
| `deep_enable_subagents` | `SubAgentMiddleware` | `task` | `__subagents` |

`SubAgentMiddleware` needs ≥1 subagent; `_general_subagent` is a minimal
general-purpose one (tuning subagents is out of scope, so they're off by default).

Drive the flag via:

```bash
just eval --baseline deep_agent --extra "--deep_enable_subagents true"
```

## Files

- `agent_code.py` — `run_agent_deep_agent` entry point + helpers `_build_deep_tools`, `_build_deep_middleware`.
- `catalog_seed.py` — `materialize_catalog_dir` and the `deep_tool_costs` cost table.
- `bash_tool.py` — `return_tool_bash`, `build_pg_env`; whitelist + metachar denylist + psql guardrail.
- `agent_code_state.py` — `DeepAgentCustomState` carries only the patience fields (no `files` state, no `captured_system_prompt`).
- `prompts.py` — `build_deep_agent_messages`; describes the on-disk catalog layout and `psql` usage, with a conditional block for subagents.
