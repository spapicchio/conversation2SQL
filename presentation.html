External Knowledge Masking

Each database has a Knowledge Base (KB). For queries with knowledge ambiguity, the relevant KB entry is deleted from the agent's view — forcing it to either ask the user or infer the formula.

Masked KB entry for this sample

{
  "id": 4,
  "knowledge": "System Unavailability",
  "description": "Proportion of time system is non-operational",
  "definition": "U = MTTR / (MTBF + MTTR)",
  "type": "calculation_knowledge"
}

The agent can discover other KB entries via get_all_external_knowledge_names but entry #4 is absent from its view.

The SQL Agent

A LangChain / LangGraph ReAct agent with a bird-coin budget system, 9 tools, and a two-stage LLM user simulator.

System Prompt (full)

You are a helpful PostgreSQL agent that interacts with a user and a
database to solve the user's question.

Task description:
Your goal is to understand the user's ambiguous question involving
external knowledge retrieval and generate the correct SQL query.
You can:
  1. Interact with the user  — ask clarifying questions or submit SQL.
  2. Interact with the database — explore schema, run queries.

The interaction ends when you submit the correct SQL or budget runs out.
Each action costs bird-coins, so you should be efficient.

Available tools and costs:
- execute_sql                      Cost: 1
- get_schema                       Cost: 1
- get_all_column_meanings          Cost: 1
- get_column_meaning               Cost: 0.5
- get_all_external_knowledge_names Cost: 0.5
- get_knowledge_definition         Cost: 0.5
- get_all_knowledge_definitions    Cost: 1
- ask_user                         Cost: 2
- submit_sql                       Cost: 3

Important strategy tips:
- First explore schema, column meanings, and relevant external knowledge.
- If intent is ambiguous, ask clarifying questions before committing to SQL.
- Ask one clarification question at a time.
- Be efficient with your actions to conserve budget.
- Test SQL with execute_sql before submit_sql when useful.
- If a submission fails and budget remains, debug and try again.
- After a successful phase-1 submission, you may receive a follow-up.

Budget Formula

Budget is computed per task by BirdInteractReader.calculate_initial_budget(): 

# 6 = ENV_INTERACT(3) + SUBMIT(3) base
# 2 × m_amb = one ask_user per ambiguity point
# 2 × patience = extra exploration tolerance
budget = 6 + 2 × m_amb + 2 × patience

For solar_panel_1: 2 critical + 1 knowledge ambiguity → m_amb = 3, patience = 3 → budget = 18 bird-coins

Agent Middleware (LangGraph hooks)

tool_wrapper_append_budget

Runs around every tool call. Deducts the tool's cost from updated_user_patience, appends the remaining budget to the tool message, and returns a Command that updates state atomically. If budget < cost (and tool ≠ submit_sql), returns a forced-submit message instead.

tool_wrapper_submit_sql

Intercepts submit_sql calls. On pass, converts the response and issues goto="end" to terminate the episode immediately — no extra model calls.

model_budget_exhausted

Runs before each model call. If updated_user_patience < 0, jumps directly to "end" — prevents the model from spending more budget on a response that can't improve the score.

Function-Driven User Simulator

A two-stage LLM pipeline that replaces a real human answering the agent's clarification questions — designed to be leak-proof, controllable, and aligned with real human behavior. (BIRD-Interact paper §3.3 & §6, ICLR 2026)

Why a Two-Stage Simulator?

Conventional LLM user simulators have two critical failure modes that invalidate evaluation:

Ground-truth leakage
The simulator reveals SQL fragments, schema details, or step-by-step reasoning the agent should not know — making the task artificially easy.
Task deviation
The simulator answers questions outside its competence (e.g. database schema questions a real user wouldn't know), distorting the interaction.

Baseline simulators fail 67.4% of unanswerable (UNA) questions — leaking forbidden information. The function-driven approach reduces this to 2.7%.

The fix: constrain the simulator's responses to a symbolic action space before letting it generate free text. The parser stage acts as a safety gate; the generator stage handles natural language variability.

Three Symbolic Actions

Action (paper)Action (code)When invoked
AMB(term) labeled("term") Question targets a pre-annotated ambiguity point. Simulator can answer from the ambiguity annotations + GT SQL.
LOC(segment) unlabeled("ALTER") Reasonable clarification not in annotated set. An AST-based retrieval locates the relevant SQL fragment from GT SQL to ground the answer.
UNA() unanswerable() Question requests schema details, GT SQL, or solution steps — things a real user wouldn't know. Simulator refuses.

Code Implementation

bird_interact_user_tools.py — the ask_user tool wires both stages together. The tool is injected with ToolRuntime[TaskData, CustomAgentState] so both stages have full access to the task context. 

def stage_1_parse_action(question, task, cfg) → str:
    messages = build_llm_as_a_parser_messages({
        'ambiguities_json': json.dumps(task.user_query_ambiguity),
        'sql_segments':     _segment_sql_and_parse(task.sol_sql),
        'clarification_question': question,
    })
    content = model.invoke(messages).content
    # extract from <s>…</s>  → e.g. 'labeled("downtime score")'
    return _extract_group_in_tag_pattern(content, 's')
        or "I'm not sure I understand your question."

def stage_2_generator(action, question, task, cfg) → str:
    messages = build_llm_as_a_generator_messages({
        "db_schema":         task.ddl_database_schema,
        "ambiguities_json":  json.dumps(task.user_query_ambiguity),
        "not_ambig_question": task.not_ambiguos_query,
        "gt_sql":            task.sol_sql,
        "sql_segments":      _segment_sql_and_parse(task.sol_sql),
        "asked_question":    question,
        "action":            action,
    })
    content = model.invoke(messages).content
    return _extract_group_in_tag_pattern(content, 's')
        or "I'm not sure I understand your question."

# The tool wires stage 1 → stage 2
def return_tool_ask_user(config_user_simulator):
    @tool
    def ask_user(clarification_question, runtime):
        action    = stage_1_parse_action(clarification_question,
                                        runtime.context, cfg)
        generated = stage_2_generator(action, clarification_question,
                                      runtime.context, cfg)
        return generated
    return ask_user

USERSIM-GUARD — Evaluation Benchmark for Simulator Robustness

A manually curated dataset of 2,100 questions (by 7 annotators) covering the three action categories in three phrasing styles (concise / normal / verbose):

AMB — Annotated Ambiguity

Questions based on the pre-annotated ambiguity points. Tests whether the simulator correctly maps to labeled ambiguities and gives accurate, constrained clarifications.

"What do you mean by 'downtime score'?"

LOC — Localizable

Reasonable clarifications outside annotated set. Annotators identify confusion points in the GT SQL (e.g., column choice, formatting, rounding) and craft questions. Answer is grounded by AST-based SQL retrieval.

"Should the result be rounded to 4 decimal places?"

UNA — Unanswerable

Intentionally inappropriate questions that probe for GT SQL, schema info, or step-by-step solution guidance. A robust simulator must refuse — baseline simulators fail 67.4% of these.

"What is the exact SQL query I should write?"

Key result: Function-driven simulator (ours) achieves 97.3% safety on UNA questions vs. 32.6% for the baseline — a 3× improvement in refusal accuracy. Evaluated using Qwen3-235B as an independent LLM-as-Judge.
