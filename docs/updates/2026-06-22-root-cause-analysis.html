Root-Cause Analysis
BIRD-Interact Text-to-SQL Agent

Five investigations into why Qwen3.5-9B fails on the interactive benchmark — what we hypothesised, what we found, and what we shipped.

Model: Qwen3.5-9B Setting: tools-only · linearized KB · 9 iters Budget: double-context (patience 12)
EXP-001 retry loops EXP-002 enum catalog EXP-003 schema grounding EXP-004 python UDF EXP-005 terminal-only
The through-line

One root cause keeps recurring

Across all five investigations, failures trace back to the same place

The agent's blockers are grounding & acting on feedback — not a lack of SQL expressive power, and not tool-parsing bugs. The 9B model hallucinates column / enum names and fails to act on explicit DB corrections.

What we expected

Doubling budget, removing tools, or adding a Python UDF would change the error rate.

What we found

Mostly the failure mode shifts, not the rate. The dominant blocker is weak schema grounding.

What we shipped

An enum-catalog injection (EXP-002) — the one fix with a verified, root-cause-linked mechanism.

EXP-001

DB / Column errors are budget-exhausted retry loops

Hypothesis: the doubled context budget lets the agent persist on broken queries longer

Problem

  • Suspected "DB Error" & "Column/Relation Not Found" submit errors rose under double_ctx_bdg.
  • Worry: more budget = more time to force-submit un-executable SQL.

Analysis

  • Dumped error distribution; traced news_4 end-to-end.
  • Correlated each error class with execute_sql count & budget exhaustion.
  • Compared against every sibling run in the series.

Hypothesis refuted   The doubled budget gave this run the lowest Column/Relation (2.7%) & DB Error (1.7%) rates in the series — failures shifted toward "Wrong SQL".

EXP-001 · root cause

A degenerate retry loop — the model ignores correct feedback

The schema is correct and Postgres returns the exact fix every time — e.g. column "occubl" does not exist … HINT: "occulbl". The agent even names the right column in its thinking, then re-emits the typo. This is the 9B model failing to act on explicit corrective feedback — not a schema/data problem.

Proposed next step

Add a loop / no-progress guard to execute_sql: detect N identical errors, then either inject a stronger HINT-quoting nudge or short-circuit to submit_sql / ask_user instead of burning budget.

EXP-002

psql_console regresses enum-heavy tasks

Two runs differ by one flag (enable_psql_console) — same pass@1 (0.387), but instances flip hard

Problem

  • Identical pass@1, yet instances swing: fake_7 0/9→6/9, mental_5 5/9→0/9.
  • The overall rate hides a failure-mode shift.

Analysis

  • Config diff: only enable_psql_console changes.
  • Per-instance error classes, tool usage, predicted SQL.
  • Inspected mental_5 system prompt + tool calls.

Confirmed   In psql mode get_schema is gone — and its DDL dump was the only source of CREATE TYPE … AS ENUM (values). \d shows only the enum type name, not its values.

EXP-002 · the fix we shipped

Restore the enum catalog the psql agent lost

The smoking gun — mental_5: the psql prompt contained 0 enum definitions and the agent never ran \dT. It guessed literals and failed every iteration: invalid input value for enum functionalimpairment_enum: "Significant" — a value lifted from the confusable functionalimprovement_enum.

Fix applied (Option B)

  • extract_enum_types(ddl) pulls every CREATE TYPE … AS ENUM out of the schema.
  • agent_code.py builds the catalog when psql is on and injects it into the system prompt (prompts.py).
  • Restores the upfront enum catalog the non-psql agent gets for free.

Verified & expected impact

  • Tests: TestExtractEnumTypes + enum cases in test_psql_console_wiring.py.
  • Re-run queued: …__psql__double_ctx_bdg_enumfix.
  • Expect DB / Column / Syntax errors to drop; mental_5, fake_9, museum_9 to recover.
EXP-003

Why psql has more un-executable SQL

Column/Relation 4.6% vs 2.7% · DB Error 3.1% vs 1.7% — and two intuitive guesses were wrong

✓ Confirmed driver

Weaker schema grounding. psql replaces clean DDL (exact names, enums, FKs) with raw \d self-introspection. Column-meaning calls collapse 2454 → 653; the model hallucinates names & mis-builds joins.

✗ Refuted #1

"\d output is truncated." — It's untruncated by design. museum_11's d.count_adequate was an enum-value hallucination, not truncation.

✗ Refuted #2

"psql meta-command calls are mis-parsed." — Only 4 of 39,003 tool calls (0.01%) malformed. Negligible.

Separate knob found: MAX_RESULT_ROWS = 3 caps SELECT rows, so SELECT DISTINCT col value-domain probes see only 3 of N — hurts discovery, but independent of the column-name errors.

EXP-003 · priorities

Where the leverage is

1
Schema grounding (highest leverage)
Extend the EXP-002 injection to also push a compact FK / relationship summary (and optionally the full column list) into the psql prompt — restoring what the DDL gave the non-psql agent without removing the console.
2
Discovery truncation (optional)
Relax MAX_RESULT_ROWS (or stop truncating single-column results) so value-domain probes aren't cut to 3 rows. Mind the token-budget tradeoff.
3
Do not harden tool-call parsing
Measured at 0.01% — not a driver. No work warranted here.
✓
Net read
Same root cause as EXP-001/002: grounding, not expressivity or plumbing.
EXP-004

Would a Python UDF tool help? Mostly no

The benchmark is formula-heavy — but the formulas are natively SQL-expressible

89%
instances carry a calculation_knowledge entry
16 / 9 / 9
GT SQLs using non-trivial math / stats / parsing
native
all resolve to SQRT / LOG / POWER / PERCENTILE_CONT

Why a UDF doesn't move the needle

  • archeology_4 0/9: formula written correctly, filtered on the wrong column — a grounding error. A UDF references the same wrong column.
  • virtual_6 0/9: faithful to the stated formula but GT used a different enum-numeric reading — an interpretation gap, not expressivity.

One scoped win

  • Copy-pasted formulas: 10 GT SQLs repeat a math sub-expression ≥2×; the heaviest repeaters all fail 0/9 (archeology cluster).
  • Defining once & calling N× removes the transcription-multiplier.

Blocked: the BIRD-Interact Postgres images don't ship plpython3u — every create_python_udf call errors until postgresql-plpython3-14 is installed. The ablation can't even be measured yet.

EXP-005 · proposed

Terminal-only baseline — the opposite extreme

Give the model only a shell; make it discover the schema, enums & values itself

Design

  • A single terminal tool (start psql-only, writes allowed); strip all curated scaffolding — no enum catalog, no get_column_meaning, no get_schema.
  • Keep only submit_sql (+ ask_user for user cells).
  • New enable_terminal_only flag, wired like existing ablations.

Open questions

  • Read-only or read-write? (write risks mutating the shared eval DB → needs isolation/rollback).
  • MAX_RESULT_ROWS=3 almost certainly must relax — self-service leans on SELECT DISTINCT.
  • Reuse double budget so the comparison isn't starved.

Hypothesis: a 9B model loses ground when structured grounding is removed (per EXP-001/002/003). Expected pass@1 flat-to-down — the value is measuring which failure classes the terminal shifts, against the read-only-console and structured-tools references.
